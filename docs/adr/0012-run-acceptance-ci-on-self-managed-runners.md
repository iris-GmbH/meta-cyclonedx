# Run acceptance CI on self-managed ephemeral runners

The dependency-free unit suite gates every pull request on GitHub-hosted runners; the kas-driven R1–R5 acceptance matrix never runs pull-request code, because GitHub's security guidance for public repositories forbids feeding untrusted fork code to self-managed machines. Acceptance therefore runs on merge events — push to a supported branch, nightly on the default branch, manual dispatch — on ephemeral, never-privileged Kubernetes runner Pods. Those Pods execute the kas tool directly (direct mode, selected only by an explicit `KAS_CONTAINER_ENGINE=none`): the runner image is built FROM the kas release image named by the submodule pin, and the harness version tie reports any mismatch as an explicit skip, so executing userland and pin move in lockstep. Running the tool from the submodule checkout instead was rejected. Cold runs against the published Yocto Project autobuilder sstate mirror are accepted economics — GitHub-hosted runners cannot fit the 25–35 GB and hours of a cold build, and shared warm-cache infrastructure is a documented upgrade path, not a prerequisite. Workflow files stay byte-identical between the maintained fork and upstream; every per-repository difference lives in configuration (runner registration, the labels variable, branch protection), so the fork stages exactly the blobs upstream will run.
